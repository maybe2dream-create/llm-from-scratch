1.credential_pii_leak_secure.py — Context Redaction 방어 흐름

ollama/d_03/credential_pii_leak_secure.py

1.1 개요

이 파일의 방어 로직은 딱 하나다 — 모델에 보내기 전에 알려진 API 키/이메일 패턴을 치환한다. 복잡한 판단 로직 없이 함수 호출 하나(redact())가 방어의 전부라서, 세 실습 중 흐름이 가장 단순하다.

1.2 함수 흐름

main() → is_ollama_available() → run_real() → redact() → ask_real() → find_sensitive() 순서로 호출된다. main()은 Ollama 연결만 확인하고 실제 로직은 전부 run_real() 안에 있다 — 이 파일에서 자체적으로 정의한 함수는 main()과 run_real() 둘뿐이고, 나머지 (is_ollama_available, redact, ask_real, find_sensitive)는 전부 다른 파일에서 가져온 것이다.

1.3 변수 흐름

USER_PASTE(마스킹 전 원문) → redact(USER_PASTE)의 반환값(치환된 문자열) → CREDENTIAL_EXTRACTION_REQUEST와 f-string으로 합쳐진 user_content → ask_real() 호출 결과 result → result.text를 find_sensitive()에 넣어 얻은 매칭 리스트. 핵심은 USER_PASTE 원본이 redact()를 거치지 않고는 어디에도 직접 쓰이지 않는다는 점이다 — 취약 경로와 코드 구조는 거의 같지만, 이 한 단계가 끼어드는지 여부가 유출 여부를 가른다.

2.multitenant_rag_leak_secure.py — tenant ACL + 출력 게이트 방어 흐름

ollama/d_03/multitenant_rag_leak_secure.py

2.1 개요

이 파일은 방어 단계가 두 겹이다. (1) 검색 전에 tenant_id로 코퍼스를 좁히는 ACL, (2) 그 결과 허용된 문서가 하나도 없으면 모델을 아예 호출하지 않고 고정 응답으로 대신하는 출력 게이트. 두 번째 단계는 실측 중 발견한 환각(hallucination) 버그를 고친 결과로 추가된 것이라서, 흐름도에도 분기(hits 가 비어있는가?)로 남아 있다.

2.2 함수 흐름

main() → is_ollama_available() → run_real() 안에서 keyword_search() → (허용된 문서가 있으면) build_prompt() → ask_real() 순서로 호출된다. 허용된 문서가 없으면 build_prompt()와 ask_real() 둘 다 건너뛰고 곧바로 고정 응답을 출력한다 — 이 분기가 바로 출력 게이트다.

2.3 변수 흐름

CORPUS(전체 문서 목록)를 requester_tenant_id로 필터링한 scoped_corpus → keyword_search()의 결과 hits → (분기) 비어있으면 그대로 종료, 아니면 build_prompt(hits, query)의 결과 user_content → ask_real()의 결과 result → result.text에서 기밀 문자열 포함 여부를 판정한 exposed. hits가 비게 만드는 것 — 즉 scoped_corpus 필터링 — 이 이 파일 전체 방어의 핵심 변수 조작이다.

3.memory_poisoning_leak_secure.py — 소유자 필터링 방어 흐름

ollama/d_03/memory_poisoning_leak_secure.py

3.1 개요

이 파일은 main()에서부터 이미 외부 참조가 시작된다 — 공유 메모리 시나리오 자체를 memory_poisoning_common.py의 build_memory_scenario() 로 만들어서 run_real()에 인자로 넘긴다. 방어 로직은 run_real() 안에서 그 메모리 목록을 요청자 소유 항목만으로 한 번 더 거르는 것이다.

3.2 함수 흐름

main() → is_ollama_available() → build_memory_scenario() → run_real() → ask_real(). 다른 두 실습과 달리 main()이 run_real()을 부르기 전에 이미 외부 함수 (build_memory_scenario())를 호출해서 데이터를 준비한다는 점이 구조적으로 다르다.

3.3 변수 흐름

build_memory_scenario()가 만든 memory 목록을 run_real()에 그대로 전달 → owner_id == current_requester 조건으로 걸러낸 own_entries → 그 텍스트를 이어붙인 context(없으면 기본 문구로 대체) → MEMORY_RECALL_QUESTION과 f-string으로 합쳐진 user_content → ask_real()의 결과 result → result.text에서 가짜 카드번호('4521') 포함 여부 판정. own_entries로 좁히는 순간 alice가 심어둔 지시문 항목은 context에 아예 들어갈 기회를 잃는다.
